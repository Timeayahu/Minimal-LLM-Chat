## 2. 轻量项目管理模型

项目采用适合单人负责、AI 协作开发的五层结构：

```text
愿景 Vision
└── 大型成果节点 Outcome
    └── 里程碑 Milestone
        └── 交付项 Deliverable
            └── 执行记录 Execution
```

### 状态定义

- `待讨论`：方向或范围尚未获得项目负责人确认。
- `已规划`：目标和完成标准已确认，但尚未开始。
- `进行中`：当前正在投入的唯一主里程碑。
- `受阻`：存在明确阻塞条件，无法继续。
- `已完成`：全部完成标准均有验证证据。
- `已取消`：经决策明确不再执行。

### 管理规则

- 同一时间只设一个主里程碑为“进行中”，减少目标漂移。
- 每个里程碑必须先写完成标准，再拆任务。
- 完成度按交付项计算，不按主观工时百分比估算。
- 新需求先判断属于哪个大型成果节点，再决定是否进入当前里程碑。
- 每轮实际开发结束后更新 `PROGRESS.md`，影响范围或优先级时同时更新本文件。
- 每完成一个里程碑，进行一次范围、架构、风险和下一里程碑评审。

## 3. 最终愿景

### 3.1 原规划中的愿景

原项目定位是：

> 构建一个小而扎实、可扩展、可研究的通用 Agent Kernel；先建立普通 Agent
> 的核心能力，再支持 Memory、RAG、不同模型和不同 Agent 风格实验。

这个方向有价值，但仍然缺少三个管理上必须明确的边界：

- 它首先是“学习载体”“个人可用产品”还是“可复用技术内核”？
- 最终主要服务什么任务：个人学习与知识、通用任务执行，还是代码工程？
- v1.0 的可验收形态是什么：CLI 应用、Python SDK、服务端 API，还是三者组合？

### 3.2 已确认的愿景方向

> Nexus Agent Kernel 首先是一个 Agent 架构学习与研究项目。项目通过亲手构建一个
> 小而完整、可运行、可观察、可替换的 Agent Kernel，系统学习 Agent 的核心组件、
> 架构取舍和工程边界，并持续吸收、验证后续出现的前沿 Agent 理念。

真实使用仍然重要，但它在项目中的角色已经明确：

- 学习与研究决定项目研究什么、为什么研究以及先后顺序。
- 真实场景用于暴露问题、验证架构和形成反馈，不以产品功能数量作为首要目标。
- 每个重要 Agent 概念都应落实为可运行代码、测试、Trace 或对比实验，避免停留在概念阅读。
- 项目不急于成为另一个 Codex 或通用聊天产品，而是先成为理解这些系统的实验底座。

### 3.3 已确认的最终形态

> Nexus Agent Kernel 最终成为一个“Agent Architecture Workbench（Agent 架构实验台）”：
> 它拥有稳定的最小内核、可替换的 Planner/Memory/Tool/Policy/Provider/Trace 组件、
> 可复现的任务与评估方式，并能够通过不同能力包研究通用 Agent、学习研究 Agent
> 和代码 Agent 的架构差异。

这个定位可以同时解决两个问题：

- 不需要现在就在“通用 Agent”与“代码 Agent”之间做不可逆选择。
- 不通过堆叠功能学习，而是通过替换组件、观察行为和比较结果学习架构。

建议采用“稳定内核 + 场景能力包”的结构：

```text
Agent Kernel
├── Runtime / Action / Context / Tool / Policy / Trace
├── 通用任务能力包
├── Agent 学习研究能力包（第一个真实使用场景）
└── Code Agent 能力包（在内核稳定后作为重要实验方向）
```

## 4. MVP 定义与非目标

### 4.1 MVP 定义

首个 MVP 不是一个面向外部用户的完整产品，而是一套可运行的
`Agent Architecture Workbench`。它必须能够：

- 清楚展示一个通用 Agent 从输入到最终回答的完整组成和数据流。
- 让工具定义、注册、选择、校验、执行、观察和错误处理都可运行、可解释。
- 让 Agent Loop 的状态、停止条件、重试、确认和失败恢复可观察。
- 用最小实验比较 workflow、自由 Agent Loop、Graph、Harness、Context 等设计理念。
- 为每个实验保存输入、配置、Trace、结果和评价，支持重复执行和对比。
- 能选取至少一个成熟开源 Agent 的设计理念，在 Nexus 中做小规模验证。

### 4.2 MVP 非目标

首轮 10 周明确不做：

- 高并发、多租户、分布式部署、企业权限系统和 SLA。
- 完整 Web 产品、移动端和商业化用户体系。
- 同时兼容所有模型、框架、向量数据库和 Agent 协议。
- 为展示“工程化”而提前增加没有替换需求的抽象层。
- 复刻完整的 Codex、Claude Code、OpenClaw 或 Hermes。
- 没有基线和评价方式的功能堆叠。

### 4.3 学习验收方法

每一个设计理念必须经过同一套研究闭环：

```text
提出问题
→ 阅读一手资料和成熟实现
→ 写出设计假设
→ 建立最小基线
→ 实现一个变量受控的实验
→ 运行相同任务
→ 对比 Trace / 结果 / 失败模式
→ 形成可复述的设计结论
```

验收不以代码行数为标准，而以项目负责人是否能够回答以下问题为标准：

- 这个设计解决什么问题？
- 它比更简单的方案多付出了什么代价？
- 什么情况下值得使用，什么情况下不值得？
- Nexus 的实验结果是否支持这项判断？

## 6. 当前状态重基线

### 已有能力（以代码和测试为准）

- OpenAI-compatible 模型调用与流式 CLI 对话。
- 多 Session 保存、加载和历史裁剪。
- `ToolSpec`、参数 schema、统一结果与结构化错误。
- 多步 `plan -> act -> observe -> final` Agent Loop。
- 工具参数校验、只读标记、危险操作确认和取消。
- 显式 `tool/final` Agent Action 协议。
- 短期 Session 与长期 Memory 分离。
- 长期记忆的类型、创建、列出、查看和删除。
- 独立 JSONL TraceStore、`run_id`、关键运行事件和最小脱敏。
- 22 个自动化测试覆盖主要 Agent、工具、Memory 与 Trace 路径。

### 主要缺口

- 现有能力尚未按成果节点执行一次完整验收。
- 当前测试主要验证实现正确性，还没有形成用于比较架构方案的 Eval 数据集。
- 缺少统一的实验定义、运行入口和结果对比方式。
- 长期记忆仍缺少检索、去重、更新、重要性和召回策略。
- 没有会话摘要和稳定用户画像。
- 没有外部知识导入与 RAG。
- 还没有系统实验 Workflow、Graph、Harness、Context Engineering 和 Multi-Agent。
- 还没有形成针对成熟 Agent 设计理念的分析与迁移方法。

### M1｜通用 Agent 解剖与最小内核

目标：不是继续堆功能，而是把现有代码变成一份可运行的 Agent 架构教材。

研究范围：

- Model、Instruction、Context、Action、Tool、Runtime、Policy、Memory、Trace 的职责。
- 工具从定义、注册、暴露给模型、参数生成、校验、执行到 observation 的完整生命周期。
- 当前教学 JSON Planner 与模型原生 Tool Calling 的协议差异。
- Agent、普通聊天模型和确定性 Workflow 的边界。

完成标准：

- [ ] 当前 Agent 主链路有一份由代码和测试共同支撑的架构地图。
- [ ] 每个核心组件都有明确输入、输出、责任和失败边界。
- [ ] 工具成功、非法参数、未知工具、确认、取消和执行失败均有回归测试。
- [ ] 建立第一组不少于 8 个任务的 Agent Eval 基线。
- [ ] 项目负责人能够不依赖文档讲清一次完整 Agent Run。

### M2｜Loop、Workflow 与 Graph Engineering

目标：理解不同编排方式如何分配“模型自由度”和“代码控制权”。

研究范围：

- 自由 Agent Loop：`plan -> act -> observe -> replan/final`。
- Prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer。
- Graph Engineering：State、Node、Edge、条件分支、循环、中断和恢复。
- Single Agent 与 Multi-Agent 的适用条件，避免把角色数量误当智能程度。

最小实验：

- 用同一任务分别实现确定性 Workflow、自由 Loop 和显式 Graph。
- 固定模型和工具，对比成功率、步骤数、可解释性和失败恢复。
- 只在单 Agent 无法清楚解决职责或上下文隔离问题时增加 Multi-Agent 版本。

完成标准：

- [ ] 至少完成 Workflow、Loop、Graph 三组可重复对照实验。
- [ ] Trace 能显示状态转换、分支依据和停止原因。
- [ ] 能说明 Graph 增加的控制力与复杂度代价。
- [ ] 形成是否以及何时引入 LangGraph 的证据化结论。

### M3｜Context、Memory 与 Knowledge Engineering

目标：理解 Agent 的能力不仅取决于 Prompt，更取决于每一步获得的完整上下文。

研究范围：

- Prompt Engineering 与 Context Engineering 的区别。
- System instruction、tools、history、observation、working state 的上下文预算。
- 短期 Session、工作记忆、长期记忆、用户画像和外部知识的边界。
- Compaction、会话摘要、按需召回、去重、重要性和遗忘。
- Memory 与 RAG 的区别；RAG 先做最小实验，不急于绑定大型框架。

完成标准：

- [ ] 能观察每轮模型实际获得的上下文组成和长度。
- [ ] 至少比较“全部注入、摘要、按需召回”三种上下文策略。
- [ ] 长期记忆具备最小检索、去重或更新能力。
- [ ] 完成一个带来源引用的最小知识检索实验。
- [ ] 能解释 Memory、Context 与 RAG 各自在 Agent 中解决什么问题。

### M4｜Harness、Tool Interface 与 Eval Engineering

目标：理解 Agent 表现是“模型 + 环境 + 指令 + 工具 + 反馈 + 评价”的系统结果。

研究范围：

- Harness Engineering：为模型设计环境、约束、反馈回路和可恢复执行条件。
- Agent-Computer Interface：工具名称、描述、参数形状、返回信息和错误如何影响模型行为。
- 权限、确认、超时、重试、幂等性、失败恢复和人类接管。
- Trace 与 Eval 的区别：Trace 用于解释一次运行，Eval 用于比较多个版本。
- Task、Trial、Grader、Metric、Baseline 和回归集。
- Skill / MCP / Tool 作为不同能力封装方式的设计取舍。

最小实验：

- 在模型和任务不变的情况下，只修改工具接口或 Harness。
- 比较基线版本与改进版本的成功率、无效步骤、错误类型和人工介入次数。

完成标准：

- [ ] 建立统一实验定义和结果记录方式。
- [ ] Eval 可重复执行并比较两个 Agent 配置。
- [ ] 至少完成一次 Tool Interface 对照实验。
- [ ] 至少完成一次 Harness 对照实验。
- [ ] 高风险工具、失败阈值和人工接管边界明确。

### M5｜前沿 Agent 设计研究与 MVP 验收

目标：证明 Nexus 已经能够用于学习前沿 Agent，而不只是实现基础功能。

研究候选：

- OpenClaw / Hermes：长期运行、Memory、Skill、个人 Agent Harness。
- Claude Code / Codex-style：代码环境、反馈闭环、权限和长任务恢复。
- LangGraph：显式状态图、确定性与模型决策混合。
- 成熟开源 Research Agent：检索规划、来源评价、并行研究和综合。

完成标准：

- [ ] 选择 2 个成熟 Agent 做结构化设计比较。
- [ ] 对每个对象区分“设计理念、实现手段、适用条件”，不只罗列功能。
- [ ] 从中选择 1 个设计理念，在 Nexus 中完成最小迁移实验。
- [ ] 使用既有 Eval 证明该设计带来的收益、代价或无效性。

## 9. 核心研究主题地图

| 主题 | 核心问题 | 在 Nexus 中的验证方式 |
|---|---|---|
| Agent Loop | 模型如何根据环境反馈持续调整行为？ | 观察步骤、停止、重试和失败路径 |
| Workflow Engineering | 哪些步骤应该由代码确定？ | 与自由 Loop 执行同一任务 |
| Graph Engineering | 如何显式表达状态、分支、循环和恢复？ | 建立最小 State/Node/Edge 实验 |
| Harness Engineering | 模型之外的环境为什么决定 Agent 能力？ | 固定模型，只改变环境、工具和反馈 |
| Context Engineering | 模型每一步应该看到什么？ | 比较全部注入、压缩和按需加载 |
| Tool / ACI Engineering | 工具接口如何影响模型行为？ | 修改 schema/描述/结果格式并跑 Eval |
| Memory Engineering | 什么值得跨轮、跨会话保存？ | 检索、去重、更新、遗忘和用户确认 |
| Eval Engineering | 如何判断架构调整真的更好？ | Task + Trial + Grader + Baseline |
| Multi-Agent | 何时需要角色和上下文隔离？ | 与单 Agent 基线比较，不默认多 Agent 更好 |

## 10. 研究资料基线

首轮研究优先使用一手资料：

- Anthropic `Building Effective Agents`：Workflow、Agent、常见编排模式和简化原则。
- Anthropic `Effective Context Engineering for AI Agents`：上下文选择、压缩和工具返回。
- Anthropic `Demystifying Evals for AI Agents`：Task、Trial、Grader、Transcript 和评估设计。
- OpenAI `Harness Engineering`：环境、意图表达和反馈回路如何支撑 Agent 可靠工作。
- OpenAI `A Practical Guide to Building Agents`：工具、指令、编排和 Guardrail。
- LangGraph 官方资料：显式状态、节点、边、循环、中断和恢复。

资料只用于建立假设，最终结论必须由 Nexus 的最小实验验证。

## 11. 风险与管理关注点

| 风险 | 影响 | 当前对策 |
|---|---|---|
| 学习目标与产品目标混在一起 | 容易只讲概念或只堆功能 | 用愿景和里程碑定义产品成果，用执行日志记录学习与实现 |
| 过早抽象 | 增加代码复杂度但没有真实收益 | 接口由多入口、多实现或高变更频率触发 |
| 路线频繁漂移 | 无法判断距离里程碑还有多远 | 同时只推进一个主里程碑，范围变化必须记录决策 |
| 文档与代码脱节 | 项目状态失真 | 里程碑完成必须引用测试或可运行证据 |
| 长期记忆写入错误 | 污染用户画像和后续回答 | 在自动记忆前建立候选与人工确认 |
| RAG 框架锁定 | 内核退化为框架 Demo | 先评审，再通过 `knowledge` 适配层接入 |
| 追逐前沿名词 | 学到术语但没有形成判断能力 | 每个主题必须完成基线、实验、Eval 和结论 |
| 工程化过度 | 时间被生产基础设施消耗 | 严格执行 MVP 非目标，需要真实问题才能增加复杂度 |
| 实验变量过多 | 无法知道结果由什么变化引起 | 每次只改变一个主要设计变量 |
| 只实现不理解 | 代码完成但无法解释设计取舍 | 里程碑验收包含口头复述和反例判断 |
