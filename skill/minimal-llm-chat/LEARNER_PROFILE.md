# 学习画像与阶段性评估

## 记录说明

本文件用于记录学生在 `minimal-llm-chat` 项目中的长期学习画像。它不同于 `PROGRESS.md` 的功能进度记录，更关注学生当前处于什么学习阶段、已经掌握了哪些概念、思考方式有什么特点、还需要补强哪些能力。

建议在完成一课、完成一次关键重构、或学生围绕某个概念连续追问并形成认知突破后更新。

---

## 2026-05-16 阶段评估：第三阶段第 13 课，命令系统重构

### 当前学习位置

学生已经从“能把功能写出来”的阶段，进入“开始理解代码为什么要这样组织”的阶段。当前处于第三阶段工程化重构的早期，正在从命令行 AI 聊天助手的小功能迭代，转向模块边界、接口设计、命令注册表、解耦和可维护性这些工程化主题。

在 AI 应用开发路径上，学生已经理解了最小 LLM 应用的基本数据流：配置读取、模型调用、messages 对话历史、JSON 持久化、多轮记忆、流式输出和多会话文件。现在开始接触 Agent 工程化前置能力：如何把命令、状态、上下文和主循环拆开，让后续 Tool Use、RAG、Session 建模更容易接入。

### 已掌握知识

- 已能理解 `.py` 文件、模块 module、包 package 的区别，并能把 `commands/` 看成一个包。
- 已理解 `__init__.py` 的作用：包入口、导入时执行、暴露公共 API。
- 已理解函数和 class 的基本取舍：函数表达动作，class 表达有身份、有状态、有行为的对象。
- 已理解类型标注 type hint 的用途，知道 `name: str`、`args: list[str]` 这类写法不是强制运行时检查，而是帮助阅读、编辑器提示和静态分析。
- 已初步理解 `ABC`、`abstractmethod` 的作用：用抽象基类规定子类必须实现的接口。
- 已理解 `self` 是实例方法接收当前对象的第一个参数，能解释为什么少写 `self` 会导致参数数量错误。
- 已理解 `super()` 的基本意义，并知道当父类方法只是抽象占位时，不应该在子类里直接 `return super().execute(...)`。
- 已理解命令注册表 registry 的意义：用命令名映射命令对象，减少主循环里的 `if/elif`。
- 已能用自己的话解释接口、封装、耦合、解耦：模块应该暴露稳定接口，调用方不应该依赖内部实现细节。
- 已能判断“一个模块可以放多个 class”，并提出按职责归类命令，比如把基础命令放进 `basic.py`。

### 掌握程度判断

整体判断：学生已经不只是照着代码写，而是在主动追问结构设计背后的理由。对工程化概念的理解处在“初步形成框架，正在通过项目巩固”的阶段。

比较扎实的部分：

- 能敏锐发现注册表相对 `if/elif` 的收益并不是绝对的，会主动质疑“这样做到底提升多大”。
- 能理解工程化不是盲目拆文件，而是根据职责、规模和变化频率决定拆分粒度。
- 能把“解耦”理解为依赖公开接口，而不是依赖内部数据结构，这说明已经开始进入软件设计层面的思考。

仍需巩固的部分：

- Python import 机制还需要更多小实验巩固，尤其是包、模块、`__init__.py`、命名空间之间的关系。
- class 的不同属性类型还需要继续练习，比如类变量、实例变量、实例方法、类方法、静态方法。
- `context` 当前还是字典，学生已经意识到它后面需要建模；下一阶段需要通过 `AppContext`、`Session`、`Message` 把这个直觉落到代码中。
- 对抽象的边界还需要继续训练：什么时候只用函数，什么时候用 class，什么时候值得加 ABC，什么时候会过度工程化。

### 学生提问特点

学生的问题有明显的工程化倾向，不满足于“代码能跑”，会追问设计是否值得、抽象是否过度、模块应该怎么划分。这是很好的信号。

本阶段高价值问题包括：

- 什么时候应该创建 class，什么时候直接写函数？
- 一个 `.py` 文件应该叫文件还是模块？
- 命令是否应该抽象出基类，并让具体命令继承？
- `self` 为什么必须写，它到底代表什么？
- `super()` 是什么，为什么 IDE 自动补全的写法不一定适合当前场景？
- `context` 是什么格式，后续是否应该建模？
- 注册表相比 `if/elif` 到底解了多少耦合？
- “完全解耦”是什么意思？是不是只依赖接口，不依赖内部细节？
- 一个模块里能不能放多个 class？为什么很多开源项目看起来是一个模块一个 class？
- `__init__.py` 到底在导入过程中做了什么？

这些问题说明学生已经从语法学习转向结构学习，正在建立“代码组织能力”和“工程判断力”。

### 老师评语

学生当前处于一个很关键的转折点：已经不再只是学习 Python 语法或照着实现小功能，而是开始从真实项目维护者的视角看代码。尤其在第 13 课中，学生对命令系统重构的价值提出了质疑：“写 if/else 好像也没什么问题”，这是非常成熟的反应。它说明学生没有盲目崇拜设计模式，而是在判断复杂度和收益是否匹配。

学生对工程化表现出明显兴趣，尤其关注模块边界、接口、解耦、注册表、包入口、class 抽象这些主题。这类问题已经接近初级开发者向工程化开发者过渡时会遇到的真实问题。当前最大的优势是愿意思考“为什么这样设计”，而不是只问“代码怎么写”。

学生的不足也很明确：底层 Python 机制还不够稳，比如 import 过程、类变量和实例变量、抽象基类与普通基类、`context` 字典和未来数据模型之间的关系，还需要通过持续编码来固化。当前不宜一下子引入过多高级模式，应继续保持“小步重构、每次只解决一个设计问题”的节奏。

总体评价：学生正处在从“功能实现型学习者”向“工程结构型学习者”转变的早期。这个阶段会有很多概念短暂混杂，比如模块、包、类、接口、API、上下文、模型等，但学生的提问质量很高，说明理解力和抽象意识已经被激活。后续只要继续把每个概念落到项目代码中，能力增长会比较扎实。

### 下一步训练建议

- 继续完成第 13 课命令系统重构，但保持小步，不要一次性迁移所有命令。
- 下一步适合迁移 `/model` 和 `/count`，因为它们属于基础命令，逻辑短，适合放进 `commands/basic.py`。
- 在迁移过程中重点观察：`main.py` 是否变薄，命令对象是否都遵守同一个接口。
- 第 14 课应重点做 `Session` 和 `Message` 建模，把学生已经提出的 `context` 建模问题自然接上。
- 每次新引入一个抽象，都要问：它解决了什么变化点？它有没有让调用方少知道一些内部细节？
